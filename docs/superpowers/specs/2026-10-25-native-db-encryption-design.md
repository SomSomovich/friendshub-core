# Проектирование шифрования нативной базы данных

## Цель

Шифровать целиком SQLite-базу, которой владеет `friendshub-core`. В ней
хранятся токены сессий и приватные ключи Signal: identity, prekey, session и
sender-key. Генерация, чтение, использование и очистка ключа остаются внутри
библиотеки. Клиент передаёт только `db_path` и не получает байты ключа.

## Требования

- Шифровать все страницы SQLite и WAL, а не отдельные столбцы.
- Создавать новую базу сразу зашифрованной SQLCipher.
- Хранить случайный ключ длиной 256 бит только в системном защищённом
  хранилище учётных данных.
- Устанавливать ключ до первого обращения к схеме на каждом соединении.
- При ошибке системного хранилища, отсутствии ключа или ошибке проверки базы
  завершать открытие с ошибкой; не создавать и не открывать plaintext-БД.
- Не преобразовывать существующую plaintext-БД. Отклонять её без изменения
  файла на всех нативных платформах.
- Не включать SQLx, SQLite и системные хранилища в WASM-сборку.
- Оставить все секретные буферы и управление памятью на стороне библиотеки.

## Вне объёма

- Шифрование IndexedDB браузерного клиента.
- Шифрование данных при передаче на backend.
- Перенос системного ключа на другой компьютер, аккаунт ОС или путь.
- Удаление ключа из системного хранилища при выходе из аккаунта.
- Импорт существующей plaintext-БД.

## Устройство

### SQLCipher

- Включить в нативный feature-граф единственный закреплённый `libsqlite3-sys`
  версии `0.37.0` с `bundled-sqlcipher-vendored-openssl`.
- Оставить SQLx слоем запросов и пула. WASM binding crate использует
  `friendshub-core` без native feature.
- Перед первым запросом к каждому соединению вызвать низкоуровневый
  `sqlite3_key`, затем настроить совместимость SQLCipher 4 и `temp_store`.
  Не помещать ключ в строку PRAGMA, опции SQLx или аргументы запроса.
- До возврата пула проверить наличие SQLCipher, чтение схемы и
  `integrity_check`.
- Не логировать ключи и не включать их в ошибки, URL или callbacks.

### Ключ и системные хранилища

- Использовать узкий внутренний интерфейс key store. Модульные тесты получают
  изолированное хранилище в памяти; файловые integration-тесты включают
  отдельный не-default feature `test-keyring`.
- В обычной библиотеке всегда выбирать системное защищённое хранилище, даже
  если другая зависимость установила process-local mock.
- Генерировать ключ через системный CSPRNG, сохранять его в key store до
  создания SQLite-файла и хранить Rust-буферы в `Zeroizing`.
- Вычислять стабильный идентификатор учётных данных из нормализованного пути
  через SHA-256. Сам ключ не записывать рядом с БД или в `Config`.
- Создавать ключ только если БД отсутствует. Для существующей БД отсутствие
  ключа — ошибка. Неверная длина или ошибка key store также завершают открытие.
- Использовать Secret Service в Linux, Keychain в macOS, защищённое хранилище
  в iOS, Credential Manager в Windows и Keystore в Android.
- В Android до открытия клиента host вызывает `fh_android_init` с `JavaVM` и
  application context. Повторная инициализация тем же контекстом допустима;
  инициализация после открытия core handle запрещена.

### Открытие базы

1. Нормализовать `db_path` и получить межпроцессную блокировку для этого пути.
2. Определить состояние файла до обращения к системному key store:
   - отсутствует — получить или создать системный ключ и только затем создать
     SQLCipher-БД;
   - начинается с SQLite plaintext-заголовка — вернуть ошибку и оставить файл
     и его содержимое нетронутыми на всех платформах;
   - любой другой существующий файл — требовать ранее сохранённый ключ, открыть
     его SQLCipher и проверить подлинность и целостность.
3. Удерживать блокировку до открытия и проверки всего пула. Она также не даёт
   двум процессам одновременно создать ключ и пустую БД по одному пути.

Для plaintext-файла клиенту нужен новый путь БД. Библиотека не экспортирует,
не заменяет и не удаляет такой файл. Никакого plaintext fallback нет.

### Перемещение и выход из аккаунта

Ключ привязан к нормализованному пути. Перемещение или переименование БД,
смена аккаунта ОС либо устройства требуют отдельного будущего re-key/import
процесса. Выход из FriendsHub не удаляет ключ. Библиотека не гарантирует
криминалистическое удаление копий, сохранённых резервными копиями, snapshot,
copy-on-write файловыми системами или flash-накопителем.

## Проверки

- Новая БД с первого байта зашифрована, повторно открывается тем же ключом и
  недоступна без него.
- Plaintext SQLite-файл отклоняется до чтения или записи key store; его байты
  остаются неизменными на всех нативных target-платформах.
- Для неизвестного/зашифрованного файла отсутствующий или неверный ключ не
  приводит к замене файла.
- Ошибка key store не создаёт БД и не возвращает незаписанный ключ.
- Каждое соединение пула получает ключ до чтения схемы.
- Открытие через Rust facade и C ABI отклоняет plaintext-файл и не возвращает
  рабочий handle.
- Существующие database/network integration-тесты проходят через зашифрованный
  пул.
- Проверить native сборку, целевые сборки Windows/Android, Apple через
  `cargo zigbuild`, а также отдельную WASM-сборку.

## Зафиксированные решения

- Полное шифрование SQLite через SQLCipher; шифрование отдельных строк не
  закрывает метаданные, индексы и остальное содержимое файла.
- Системное хранилище обязательно. Никаких файловых, plaintext или других
  fallback для ключа.
- Существующая plaintext-БД не переносится; открытие отвергается без изменения
  файла. В production-клиентах с этой библиотекой таких баз нет.
- Для Android оставить минимальный host bridge контекста; владение ключом
  остаётся у библиотеки и Keystore.
- `db_path` остаётся частью конфигурации; ключ не добавляется в Rust API или
  C ABI.
- Блокировка открытия остаётся для сериализации key store и создания новой
  базы между процессами.
- Формат SQLCipher фиксируется на совместимой конфигурации SQLCipher 4.
  Обновление зависимостей должно подтверждать совместимость ранее созданных
  зашифрованных баз.
- Нулевое заполнение контролируется для Rust-буферов. Нельзя обещать очистку
  всех копий внутри SQLite, OpenSSL или операционной системы.
